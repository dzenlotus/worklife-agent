# Быстрый старт Worklife

Доведи пользователя до рабочего поиска за один короткий проход. Сам проверь и настрой доступное; человеку оставь только отсутствующий выбор, вход, код и согласие на конкретное внешнее действие. Не обещай фиксированное время авторизации у провайдера.

## Один проход

1. Вызови `recruiter_start`, `connectors_list`, `blockchain_status`; прочитай `records_list(bucket="research")`, а при необходимости `account`, `platform`, `cv`, `schedule`. Используй существующие условия, CV, доступы и прежний мандат. Не запускай анкету повторно и не исполняй незавершённые черновики при проверке подключений.
2. Собери отсутствующее в один короткий вопрос: цель/условия, где искать и получать ответы, назначение Telegram. Запрашивай только то, что меняет следующий шаг. Пока человек входит в сервис, продолжай независимую настройку. Если профиль пуст, получи минимум цели и условий через `worklife-intake`; CV импортируй через `worklife-match-cv`. `profile_save` заменяет весь объект: объединяй изменения с текущим профилем. Не выводи географию из языка.
3. Подключи необходимые источники и каналы по таблице. «Всё нужное» не означает регистрацию на всех площадках или платную подписку. Используй уже подключённые MCP/браузер/API, не ограничивай подбор встроенными адаптерами. Настройка доступа не даёт права отправлять отклики и письма работодателям.
4. Проверь реальные чтения, сохрани результат и перейди к ближайшему разрешённому действию. Ошибка одного провайдера не блокирует остальные шаги; после ошибки входа/лимита не повторяй попытки по кругу. Если поиск отложен, проверяй доступ без запуска поиска.

## Подключения и проверка

`connectors_list` показывает настройки и наличие переменных, а не действующий вход. Имена адаптеров бери из результата. Новые создавай через `connector_configure(name,config)`; секреты передавай только ссылками `*_env`/`headers_env`. Сохраняй обнаруженные площадки и фактический статус аккаунтов через `platform_save`/`account_save`.

| Канал | Проверка и следующий шаг |
| --- | --- |
| Публичные вакансии | Для HH/Greenhouse/Lever используй `jobs_search(connector,query,parameters,language)`, а не `connector_read` с операцией search. HH допускает `parameters={"per_page":1}`; Greenhouse/Lever требуют реальную доску `board`. Один малый запрос по сохранённой цели достаточно для проверки; это ещё не обзор рынка. |
| Личный HH и другие площадки | HH: `connector_read(connector,"me")`, затем при необходимости `resumes`. Публичная выдача не доказывает вход в аккаунт. OAuth/вход проходит у провайдера; конфигурация токена его не выдаёт. Другие сайты — существующий MCP, разрешённый API либо `browser_open`/`browser_inspect`. Не меняй пользовательский профиль сайта ради проверки. |
| Почта | Используй имеющийся ящик. Для `email` нужны реальные SMTP/IMAP-настройки и ссылки `from_env`, `username_env`, `password_env`. Проверь `connector_read(connector,"inbox",{"limit":1})`: чтение без отправки и отметки прочитанным. Успешный IMAP не доказывает SMTP-доставку. Для AgentMail используй уже настроенные HTTP-операции; адрес `email` и внутренний `inbox_id` различаются. Новый ящик создавай только в согласованном объёме. |
| Произвольный API, например SuperJob | Настрой тип `http` с поддержанными провайдером `operations` и `headers_env`; выполни настоящую read-операцию через `connector_read`. Не отправляй его в `jobs_search`: этот инструмент не обрабатывает HTTP-коннекторы. Неизвестную схему проверь по документации провайдера. |
| Telegram | Сначала определи назначение по следующему разделу. Успех одного варианта не означает подключения остальных. |

Входные токены, пароль, код Telegram и сессия вводятся в личном локальном окружении/окне входа, не в чате, аргументах MCP или `research_note`. MCP не записывает переменные окружения. В MCP-only клиенте найди несекретные пути Python и личного env-файла в сохранённой заметке/отчёте установки. Если они недоступны, одним вопросом запроси эти пути или настройки запуска с удалёнными значениями секретов; не выдумывай пути. Подготовь конкретную команду для машины пользователя и продолжи доступные MCP-шаги.

## Telegram до рабочего состояния

- **Общая база работодателей:** личный аккаунт MTProto и служебная группа. Каждый участник получает собственные `api_id`/`api_hash` на [my.telegram.org](https://my.telegram.org). Этот транспорт обменивается публичными блоками; CV и переписка в него не входят.
- **Сообщения от бота:** `connector_configure(name,{"type":"telegram","token_env":"TELEGRAM_BOT_TOKEN"})`, затем `connector_read(name,"updates",{"limit":1})`. Это Bot API, он не подключает личную переписку или историю служебной группы. Не забирай updates у бота, уже обслуживаемого другим процессом, без согласования этого использования.
- **Личная переписка:** используй уже авторизованный Telegram MCP/юзербот, если он доступен. Встроенный бот и транспорт общей базы его не заменяют; если такого инструмента нет, явно укажи недостающий доступ.

Для общей базы проверь `telegram` extra **в том же постоянном Python-окружении, которым запущен MCP**. В исходниках: `uv sync --extra telegram` (сохрани остальные extras). В установленном окружении добавь Telethon по ограничению пакета: `uv pip install --python <MCP_PYTHON> 'telethon>=1.45,<2'`; не обновляй Worklife из PyPI поверх текущей локальной версии ради одной зависимости.

Если готовой авторизованной сессии нет, используй [scripts/telegram_login.py](scripts/telegram_login.py). Подготовь команду с реальными абсолютными путями и открой пользователю терминал для самостоятельного скрытого ввода:

```sh
<MCP_PYTHON> <SKILL_DIR>/scripts/telegram_login.py --env-file <PRIVATE_ENV_FILE>
```

Без доступа к папке скилла тот же помощник доступен в установленном пакете:

```sh
<MCP_PYTHON> -c "from worklife.agent_profile import BUNDLE_DIR; import runpy; runpy.run_path(str(BUNDLE_DIR / 'skills/worklife-onboarding/scripts/telegram_login.py'), run_name='__main__')" --env-file <PRIVATE_ENV_FILE>
```

Помощник запрашивает API ID/hash, телефон, код и при необходимости 2FA; использует готовую сессию повторно, сохраняет её после успешного входа в файл с правами 0600 и не выводит секреты. При нестандартных именах из `network.telegram` передай `--api-id-env`, `--api-hash-env`, `--session-env`. Подробности сессий: [Telethon](https://docs.telethon.dev/en/stable/concepts/sessions.html).

Свяжи этот файл с запуском MCP через `--env-file`: обнови только этот аргумент существующей записи `worklife_recruiter`, сохранив её Python, `--config`, `--home`, окружение и остальные настройки. Если файл уже подключён, достаточно перезапуска. При использовании установщика сначала прочитай прежние параметры и `worklife-recruiter install --help`; сохрани прежние target, destination, config/home и область установки. Не создавай другую личную базу. Перезапусти подключение MCP: уже запущенный процесс не прочитает новый файл, а заданные клиентом переменные имеют приоритет над ним. Повтори `recruiter_start` и убедись, что вернулся прежний профиль.

Для обычного участника используй общую группу, к которой он уже присоединился: `blockchain_telegram_connect(chat)` после разрешения публиковать туда общие блоки. Новую приватную группу создавай через `blockchain_telegram_create_group(title)` только по просьбе создать её; прежняя такая просьба сохраняет силу. Новая группа не подключает к уже существующим участникам автоматически и никого не приглашает.

Запусти `blockchain_sync()` и проверь **`telegram.status == "healthy"` в его результате**, затем `blockchain_status`. `connect` лишь сохраняет выбор; общий healthy и кеш состояния не доказывают доступ Telegram. Нулевые счётчики допустимы, но не доказывают обмен двух участников. После подключения фоновый обмен требует работающего app/MCP/worker.

## Завершение и продолжение

Сохрани `research_note` с названием «Онбординг Worklife», временем проверки, результатом по каждому нужному каналу, точной ошибкой без секретов и следующим действием. Статусы: проверено / настроено, не проверено / нужен вход или выбор / пропущено пользователем. При повторном запуске перечитай последнюю запись и проверь изменившиеся доступы; не считай старый успех вечным.

Покажи коротко: что готово, что требует участия человека, ближайший шаг. Не отмечай весь онбординг завершённым, пока выбранное подключение не проверено. Отправку проверяй только при отдельном разрешении и конкретном получателе через `action_draft` → `action_approve` → `action_execute`. Расписания включай лишь по просьбе об автоматической работе; отдельный ключ модели для агента в MCP-клиенте не нужен. При разрешённом поиске переходи к `worklife-market`.
