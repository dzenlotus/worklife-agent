# P2P на устройствах участников

Участник запускает Worklife на своём компьютере. Узлы находят друг друга через
HyperDHT и передают публичные блоки по зашифрованным Noise-соединениям Hyperswarm.
Аренда VPS, домен, аккаунт GitHub, платный API и ручное разрешение администратора
для этого не требуются. Участники используют собственные устройства, электричество
и существующее подключение к интернету.

Узлы обнаружения сообщают, где искать участников. Они не подтверждают записи,
не выдают права и не выбирают принятую цепочку. Каждый участник самостоятельно
проверяет подписи, квалификацию и PoW по прежним правилам. Публичный профиль
`public-testnet-v1` сохраняет 25 бит работы на блок, 18 бит квалификации и шесть
подтверждений. Число созданных ключей не добавляет веса цепочке.

## Запуск на своём компьютере

Нужны Python 3.12+, Node.js 24 с npm и установленный Worklife. Из исходников:

```sh
uv sync
WORKLIFE_CHAIN_PROFILE=public-testnet-v1 uv run worklife --home ~/.worklife-p2p p2p setup
WORKLIFE_CHAIN_PROFILE=public-testnet-v1 uv run worklife --home ~/.worklife-p2p p2p run
```

`setup` один раз устанавливает закреплённые зависимости транспорта через npm.
`run` соединяется с общедоступной сетью обнаружения HyperDHT и обменивается
публичными блоками. Для начального запуска нужен интернет; аренда своего узла
обнаружения не нужна. Отдельный HTTP-сервер и список HTTP-адресов участников
не требуются.

Для добровольного участия в квалификации и добыче:

```sh
WORKLIFE_CHAIN_PROFILE=public-testnet-v1 uv run worklife --home ~/.worklife-p2p p2p run --mine --cpu-fraction 0.25
```

`--cpu-fraction` задаёт среднюю долю CPU-времени рабочего процесса с паузами,
а не предел для всей машины. Без `--mine` узел только проверяет и распространяет
блоки. Остановка через Ctrl+C сохраняет данные; для повторного запуска используется
та же папка `--home`.

В другом терминале:

```sh
WORKLIFE_CHAIN_PROFILE=public-testnet-v1 uv run worklife --home ~/.worklife-p2p p2p status
WORKLIFE_CHAIN_PROFILE=public-testnet-v1 uv run worklife --home ~/.worklife-p2p chain status
```

`p2p status` показывает состояние работающего транспорта, проверенные соединения
и счётчики обмена. Поле `neighbors` показывает число основных, пробных и входящих
соседей, ожидающие подключения, размер списка кандидатов и признак `degraded`.
Снимок находится в `p2p-status.json` внутри папки узла.
После остановки процесса это последний сохранённый снимок.

Узел продолжает искать соседей и при работающих соединениях: первая повторная
попытка следует через пять секунд, последующие — через 30–35 секунд со случайной
задержкой. Это помогает восстановить сеть после перезапуска узлов обнаружения
и находить новые пути обмена. Для нового подключения по-прежнему нужен хотя бы
один доступный источник обнаружения либо сохранённый доступный сосед.

При желании можно явно указать доступный UDP-узел обнаружения:

```sh
WORKLIFE_CHAIN_PROFILE=public-testnet-v1 uv run worklife --home ~/.worklife-p2p p2p run --bootstrap participant.example:49737 --port 49737
```

Замените адрес действующим адресом участника, который предоставляет обнаружение;
покупать указанный пример домена не нужно. Несколько `--bootstrap` задают несколько
таких адресов. Это способ найти сеть, а не список доверенных подтверждающих.
`--isolated` отключает публичные узлы обнаружения; он предназначен для отдельного
локального испытания. `--room` отделяет испытательные группы внутри того же
genesis и не меняет правила консенсуса. Для общей сети эти параметры не нужны.

Папка узла содержит отдельный ключ транспорта `p2p-identity.key` и авторский ключ
Worklife. Каждый участник создаёт свои ключи автоматически. Для сохранения своей
идентичности сохраняйте собственную папку; не раздавайте её копии другим участникам.
Для другого профиля сети нужна отдельная папка.

## Как узел выбирает соседей

По умолчанию узел допускает до 32 соседей: восемь основных, которых выбирает сам,
два пробных и до 22 остальных входящих. Поток незапрошенных входящих соединений
не занимает десять мест, оставленных для собственного выбора. Одновременно
транспорт начинает не более трёх исходящих подключений; остальные выбранные
кандидаты ждут своей очереди. Если два узла одновременно подключились друг
к другу, замена дублирующего соединения сохраняет первоначальный выбор узла.

Список кандидатов ограничен 256 ключами. От одной наблюдаемой группы адресов
узлов обнаружения сохраняется до восьми новых непроверенных кандидатов.
При выборе сначала сравниваются группы источников, затем ключи внутри группы:
публикация тысячи ключей через один источник сама по себе не даёт ему тысячу
долей в выборе. Источник обнаружения и адрес установленного соединения
учитываются отдельно. Адрес из сообщения самого участника для этого не используется.

Группировка объединяет близкие IPv4-адреса в `/24`, IPv6-адреса — в `/48`.
Для установленного соединения используется адрес маршрута, который видит
транспорт. При передаче через ретранслятор это может быть адрес ретранслятора.
Разные группы адресов не доказывают, что узлы принадлежат независимым людям,
а одинаковая группа не означает одного владельца.

Узел сохраняет до 32 соседей, с которыми полностью завершился проверенный обмен
публичными блоками. Одного успешного Noise-соединения или сообщения `hello`
недостаточно. Эта история используется при повторном запуске и отделена
от непроверенных объявлений: поток новых объявлений не вытесняет её.
Файл находится рядом с `p2p-identity.key`, содержит тему сети в имени
и доступен только владельцу папки (права `0600`). История относится к конкретной
теме сети, включая выбранную испытательную группу `--room`.

Пробные соединения обновляются через 60 секунд. Проверенный пробный сосед
из новой наблюдаемой группы может заменить основного соседа из повторяющейся
группы. Когда доступно мало разных маршрутов, в том числе за общим NAT,
узел продолжает обмен и показывает `degraded: true` при недостаточном
разнообразии основных соседей. Общий NAT не служит причиной общего запрета
на подключение участников.

Эти меры затрудняют eclipse-атаку, при которой злоумышленник занимает окружение
узла своими соседями и скрывает честную цепочку. Они не гарантируют доступ
к честному участнику, если злоумышленник контролирует все доступные источники
обнаружения и маршруты обмена. Проверка соседей также не заменяет защиту
консенсуса от захвата большинства вычислительной мощности.

## Запуск через Docker

Собрать образ из проверенного исходного дерева:

```sh
docker build -f deploy/p2p-network/Dockerfile -t worklife-p2p:local .
docker run --rm -it --name worklife-p2p -p 49737:49737/udp -v worklife-p2p-data:/data worklife-p2p:local p2p run --port 49737
```

В образ включены Node.js, закреплённые зависимости транспорта и Python-приложение;
при запуске npm ничего не скачивает. По умолчанию образ использует
`public-testnet-v1`. Для добычи добавьте `--mine --cpu-fraction 0.25` в конец команды.
Том `worklife-p2p-data` сохраняет цепочку и собственные ключи при пересоздании
контейнера. Файл состояния можно прочитать без HTTP:

```sh
docker exec worklife-p2p worklife p2p status
```

Проброс UDP-порта помогает входящим соединениям, если сеть их допускает.
Hyperswarm пробует установить соединение через NAT, но работоспособность за любым
NAT, корпоративным фильтром или блокировкой UDP не гарантируется. Для проверки
между разными интернет-подключениями нужны реальные устройства в этих сетях.

## Воспроизводимая локальная проверка

`deploy/p2p-network/compose.yaml` — отдельный изолированный стенд. Он запускает
трёх участников с разными томами и ключами и четыре узла обнаружения без томов,
цепочки и прав подтверждения. Для определения NAT HyperDHT нужны измерения как
минимум с трёх разных IP; один маршрутизатор в такой изолированной сети недостаточен.
Сеть Docker помечена `internal`, публичная DHT
в этом испытании не используется. Команды ниже создают только локальные контейнеры:

```sh
docker build -f deploy/p2p-network/Dockerfile -t worklife-p2p:local .
python3 scripts/verify_p2p_network.py --image worklife-p2p:local
```

Сценарий использует сохранённые 15 настоящих блоков из
`tests/fixtures/p2p-public-blocks.json`, включённых в репозиторий и ранее добытых
при правилах 25/18/6. Он не подменяет доказательства и не снижает сложность:

1. Проверяет, что A, B и C начинают с одного genesis и пустых отдельных хранилищ.
2. Импортирует первые десять блоков только в A. B и C получают их через P2P;
   сценарий ждёт также проверенного прямого соединения между B и C.
3. Останавливает все четыре узла обнаружения и A. Импортирует оставшиеся пять блоков только
   в B и проверяет, что C получает их по оставшемуся соединению, достигает того
   же head и самостоятельно видит шесть подтверждений синтетической записи.
4. Снова запускает обнаружение для нового подключения, пересоздаёт C и проверяет
   сохранение его авторского ключа, ключа транспорта, head и подтверждения.
   Первоначальный источник A остаётся выключенным.

Итог, снимки состояния и журналы записываются в
`artifacts/blockchain/p2p-three-node/`. Сценарий завершает только контейнеры своего
уникального проекта и оставляет его тома. `--project` позволяет задать другое
имя; существующий проект с данными не переиспользуется. `--timeout 300` задаёт
общий срок проверки. При `--build-context /path/to/reviewed/source` сценарий
сначала соберёт образ из указанного дерева.

Эта проверка подтверждает передачу и проверку настоящих блоков, продолжение
существующего обмена без начального обнаружения и сохранение состояния после
перезапуска. Новая добыча, независимые владельцы узлов, доступность за внешними
NAT и устойчивость к захвату большинства вычислительной мощности требуют
отдельной проверки. Устройство должно оставаться включённым, чтобы участвовать
в обмене; уже полученные копии сохраняются у других участников.

## Проверка безопасности

```sh
uv run pytest -q tests/test_p2p_security.py tests/test_p2p_protocol.py tests/test_p2p_runtime.py
npm ci --prefix src/worklife/p2p_transport --omit=dev
npm test --prefix src/worklife/p2p_transport
node scripts/simulate_p2p_neighbors.mjs
```

Проверки используют временные папки и синтетические ключи. Они проверяют отказ
в запросах к профилю, резюме и ключам, отсутствие выполнения команд пира,
неизменность цепочки при подделке подписи, работы, квалификации или повторе
события, а также изоляцию неверных, слишком больших и глубоко вложенных сообщений.
Перебор типов входных полей проверяет, что исправный участник продолжает обмен.
`npm test` автоматически запускает все файлы тестов транспорта, включая
проверки выбора соседей и настоящих локальных Noise-соединений.

Сценарий `simulate_p2p_neighbors.mjs` моделирует выбор соседей без сетевого
трафика. В 128 парах запусков с одинаковыми начальными условиями он сравнивает
один и тысячу враждебных ключей из одной группы источников на фоне 16 других
групп: число выделенных враждебной группе основных и пробных мест совпадает
в каждой паре. Отдельные сценарии проверяют, что:

- Тысяча незапрошенных входящих попыток занимает не более 22 мест и оставляет
  восемь основных и два пробных места для собственного выбора.
- Тысяча непроверенных объявлений сохраняет все 32 записи полезной истории.
- Тысяча последовательно подключённых и проверенных ключей с одного адреса
  оставляет 31 прежнюю запись из разных групп при пределе истории 32.
- Участники за общим NAT продолжают обмен, а ограниченное разнообразие
  отмечается признаком `degraded`.

Это результаты указанных локальных сценариев и модели выбора, а не измерение
устойчивости реальной публичной сети или доступности через внешние NAT.

Отдельный тест `flood.test.mjs` создаёт настоящие локальные Noise-соединения,
на короткое время задерживает чтение транспорта и отправляет меньше 20 МиБ
синтетических сообщений. До исправления переполнение общей очереди завершало
транспорт с кодом 1. Теперь транспорт приостанавливает чтение до освобождения
очереди, а превышение жёсткого лимита отключает отправителя. Тест проверяет,
что процесс остаётся жив и другой участник передаёт контрольное сообщение.

Прямое P2P-соединение раскрывает сетевой адрес участника другим узлам. Шифрование
соединения не делает IP-адрес анонимным; наблюдаемый адрес при ретрансляции
может принадлежать ретранслятору. В обмен допускаются только публичные
блоки; личный профиль и файлы остаются локальными. Публикация записи самим
пользователем делает её содержимое доступным получателям блоков.

Эти проверки ограничены перечисленными сценариями. Они не доказывают
устойчивость к длительной распределённой перегрузке, захвату большинства
вычислительной мощности или доступность за каждым вариантом NAT. Для малого
публичного тестнета захват большинства мощности остаётся существенным риском;
число ключей само по себе вес цепочке не добавляет.

Проверка `hello` не требует квалификации или PoW. Сам факт завершённого обмена
не доказывает честность соседа. Сохранённая история, собственный выбор,
пробные подключения и разнообразие наблюдаемых маршрутов снижают зависимость
от одного окружения, но не доказывают независимость владельцев узлов.
