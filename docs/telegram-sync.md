# Общая база через Telegram

Каждый экземпляр Worklife хранит собственную базу. Служебная группа Telegram доставляет
файлы с подписанными блоками между экземплярами. Импорт проверяет существующие правила
сети, подписи, PoW, квалификацию и связи блоков. Истинность сведений о работодателе
по-прежнему оценивается по источникам.

Telegram остаётся централизованным транспортом: блокировка аккаунта, удаление истории
или недоступность группы мешают доставке. Локальные проверенные копии сохраняются.

## Подключение

Telegram подключается по желанию пользователя. Без выбранной служебной группы Worklife
работает с локальной базой и другими настроенными транспортами, не запрашивая доступ к Telegram.
В пакет входят интеграция и команды подключения; каждый пользователь использует собственные
API ID/API hash и сессию своего аккаунта.

Пользователь, решивший подключить Telegram, регистрирует приложение в разделе
**API development tools** на [my.telegram.org](https://my.telegram.org), получает свои
`api_id` и `api_hash`, затем авторизует свой аккаунт. Порядок описан в
[официальной инструкции Telegram](https://core.telegram.org/api/obtaining_api_id).

Установите дополнительную зависимость:

```sh
uv sync --extra telegram
```

Для установки из пакета: `pip install 'worklife-agent[telegram]'`.
Настройте пользовательский аккаунт MTProto с API ID, API hash и авторизованной строкой
сессии Telethon. Готовую строковую сессию Telegram MCP можно использовать через те же
имена переменных. Это доступ ко всему аккаунту, хранить его следует только в личном
окружении или `.env`, исключённом из Git. В чат, обычные записи и аргументы MCP секреты
не передаются. Bot API token для чтения истории этим транспортом не используется.

Имена по умолчанию: `TELEGRAM_API_ID`, `TELEGRAM_API_HASH`, `TELEGRAM_SESSION_STRING`.
Сессия должна быть авторизована заранее: фоновая синхронизация не запрашивает код входа.
Скилл [worklife-onboarding](../src/worklife/agent_bundle/recruiter/skills/worklife-onboarding/SKILL.md)
включает локальный помощник `scripts/telegram_login.py --env-file /absolute/path/private.env`:
он запрашивает код и 2FA в терминале, сохраняет сессию после проверки аккаунта и не выводит её.
Запускайте его Python-интерпретатором постоянного окружения Worklife, затем подключите файл
через `--env-file` при запуске MCP и перезапустите соединение.
См. [строковые сессии Telethon](https://docs.telethon.dev/en/stable/concepts/sessions.html).

Обычный участник присоединяется к общей служебной группе и выбирает её командой
`telegram connect`, приведённой ниже. Регистрация собственного API-приложения
не требует создания отдельной группы: участники синхронизируются через одну общую группу.

Если организатор обмена хочет создать новую служебную супергруппу, он выполняет:

```sh
uv run --extra telegram --env-file .env worklife --config config.toml telegram create-group
```

Команда никого не приглашает. Владельцу группа доступна в его Telegram.
Прежняя история явно включается для будущих участников, чтобы новая копия могла загрузить базу с начала.
Других участников владелец добавляет обычными средствами Telegram; отдельные аккаунты
подключаются к этой же группе с собственными сессиями. Публикация в обычный канал
требует права администратора; супергруппа допускает общую запись участников.

Выбрать уже доступную аккаунту группу, проверить состояние и выполнить обмен:

```sh
uv run --extra telegram --env-file .env worklife --config config.toml telegram connect -1001234567890
uv run --extra telegram --env-file .env worklife --config config.toml telegram status
uv run --extra telegram --env-file .env worklife --config config.toml telegram sync
```

Вместо ID можно указать `@username` или публичную ссылку `https://t.me/username`.
Выбор сохраняется в личной базе и действует после перезапуска. Его можно задать
через `[network.telegram]` в config.toml; сохранённый выбор команды имеет приоритет:

```toml
[network.telegram]
chat = "-1001234567890"
api_id_env = "TELEGRAM_API_ID"
api_hash_env = "TELEGRAM_API_HASH"
session_env = "TELEGRAM_SESSION_STRING"
```

В MCP доступны `blockchain_telegram_create_group`, `blockchain_telegram_connect`,
`blockchain_sync` и `blockchain_status`, включая профиль Recruiter. Создание группы
требует просьбы пользователя, выбор группы — разрешения публиковать туда общие блоки.
После подключения работающий app, MCP или worker выполняет обмен автоматически,
не чаще раза в минуту без локальных изменений. `network.auto = false` или
`WORKLIFE_NETWORK_OFFLINE=1` отключает фоновый обмен; явная команда sync доступна.
Майнинговый `chain worker` также использует этот транспорт с собственным интервалом.
`blockchain_status.synchronization` показывает последнее состояние транспорта без сетевого запроса.

## Доставка и восстановление

Файлы `worklife-blocks-v1.json` содержат только `protocol`, `network`, `genesis`,
`rules` и `blocks`. Максимум — 100 блоков и 8 МиБ на файл. Личные таблицы,
CV, почта, контакты и неподтверждённые предложения не экспортируются. Переписка
с работодателями через Telegram MCP остаётся отдельным процессом.

Получатель читает историю от сохранённой позиции, проверяет блоки существующим
импортом и пропускает дубликаты. Принятые записи не публикуются повторно в ту же
группу. Новый участник начинает с начала доступной истории; после отключения
экземпляр догружает пропущенное. Неверные пакеты не исполняются и не становятся
инструкциями модели.

Если родитель блока ещё не получен, сохраняется позиция перед таким сообщением.
Следующие сообщения всё равно читаются; после появления родителя следующий цикл
повторно проверяет отложенную часть истории. Это простое решение для небольшой сети:
долго отсутствующий родитель приводит к повторному чтению истории. Ошибка чтения
или отправки не помечает недоставленные блоки как успешно переданные.

Оба участника должны выбрать один `WORKLIFE_CHAIN_PROFILE` до запуска процесса.
Для public-testnet используется `public-testnet-v1`; профиль development с ним
несовместим. Telegram-порядок сообщений не меняет правила выбора ветки цепочки.

## Проверка

```sh
uv sync --extra dev --extra telegram
uv run --no-env-file pytest -q tests/test_telegram_sync.py tests/test_telegram_transport.py tests/test_telegram_integration.py
```

Проверки используют настоящие подписанные блоки и локальную историю доставки:
обмен двух экземпляров, перезапуск и догрузка, подключение пустой третьей базы,
дубликаты, перепутанный порядок предков, неверные подписи и изоляция личных данных.
Транспортные тесты проверяют вызовы Telethon без обращения к реальному аккаунту.
Сетевую приёмку проводят отдельно после авторизации аккаунтов и создания группы.
